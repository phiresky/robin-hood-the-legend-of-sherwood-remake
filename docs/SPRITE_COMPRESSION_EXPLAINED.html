The Sprite Codec

How the Robin Hood port compresses its pre-rendered sprites 2.3× past zstd: vector-quantized tiles, adaptive context modeling, and coding characters against each other.

robin hood rust port · august 2026 · companion to docs/COMPRESSION.md

1 What we are compressing

The game’s characters are pre-rendered 3D: every character was rendered once per action × animation frame × 16 camera directions, producing 4,000–8,000 unique small images per character (RobinTown: 7,584 frames, average 37×56 pixels). Pixels are RGB565 (16-bit color) with two reserved values: a transparent key (0x07C0) and a shadow key (0x001F).

Three generations of compression have touched this data, and it matters to keep them apart:

The original engine’s two sprite representations:

RLE sprites (menus, patches, accessories): each scanline stores [first_x, last_x, pixels…], skipping transparent margins.

VQ sprites (all characters): vector quantization. Each character gets a dictionary of 4,096 tiles, where a tile is 4 horizontally adjacent pixels . A sprite is then a grid of (width/4) × height dictionary indices. Twelve bits describe four pixels (3 bits per pixel before any entropy coding), and the 32 KB dictionary holds all the color data. Decode is a table lookup; the quantizer ran once at authoring time.

So a “character” on disk is one dictionary, a few thousand index grids, and animation metadata. The grids are the bulk: RobinTown’s hold 3.9 million 12-bit indices, 7.8 MB as raw words.

2 Why zstd stalls: the order-0 wall

The port’s earlier schemas compress the serialized bank with zstd (level 22, long-range matching). That beats raw storage 2.5×: RobinTown’s grids go from 7.8 MB to 3.09 MB. The question is how much more is available.

Information theory gives a yardstick. Count how often each of the 4,096 index values occurs and ignore everything else: an ideal coder using those frequencies alone needs 6.14 bits per tile, the order-0 entropy, or 3.01 MB. zstd landed at 3.09 MB, within 3% of that limit.

An LZ compressor saves bytes by finding exact byte repeats earlier in the stream. The structure in the index grids is two-dimensional: the tile above a cell is the same image content one pixel row up, and predicts it well. In the row-by-row stream, vertically correlated tiles sit width/4 symbols apart with unrelated tiles between them, so exact repeats long enough for LZ to use are rare.

3 The codec in one sentence

For every tile, predict a probability distribution over the 4,096 possible indices from the tiles above and to the left (already decoded), feed that distribution to an arithmetic coder, and update the statistics. The decoder runs the same statistics in lockstep, so no model is ever transmitted.

3a · Adaptive contexts (the PPM family)

A context is what we know when predicting a tile; here, the pair (above-tile, left-tile). For each context the codec keeps counts of which symbols followed it before. RobinTown develops ~500,000 distinct contexts, and most are extremely sharp: a context that has produced tile #1712 fifty times in a row predicts it at over 98%.

Sharp contexts have a weakness: the first time a context meets a new symbol it has no count for it. PPM (Prediction by Partial Matching, the family behind RAR and 7-Zip’s PPMd) solves this with an escape chain: every context reserves a little probability for “none of my known symbols,” and on escape falls back to a simpler context:

(above, left)  →  above  →  left  →  no context  →  uniform over 4096

Two refinements matter measurably:

Exclusion (−3%): when (above, left) escapes, the fallback level must not waste probability on symbols the escape already ruled out; the codec subtracts them from the fallback’s interval.

SEE, secondary escape estimation (−1…4%): how much probability to reserve for escapes is itself learned, in buckets keyed by chain level, context size, context maturity, and how dominant the context’s top symbol is. The fixed heuristics (PPMC’s one count per distinct symbol, PPMD’s half counts) both measured worse on this data.

Adaptation is slow: increment 1, halve counts on saturation. The streams are stationary within a character, and a faster increment measured 4–9% worse.

3b · Arithmetic (range) coding

Given “the model says this tile has probability p,” an arithmetic coder emits exactly −log₂(p) bits, so a sharp prediction costs a fraction of a bit. Ours is the LZMA-style range coder: a 32-bit interval repeatedly narrows in proportion to symbol probabilities and renormalizes a byte at a time. Coder overhead is a few bytes per million symbols; the compression ratio is determined by the model.

rANS was considered and rejected. It emits symbols last-in-first-out, which suits static probability tables but not adaptive models: the decoder must replay model updates in encoder order, and that is the order rANS does not provide. A FIFO range coder has no such conflict.

3c · The decoder is the encoder

There is no model in the file. Encoder and decoder run identical code over identical state: both start empty, update counts after every symbol, halve at the same thresholds, consult SEE identically. Every model improvement costs zero format bytes. It also means every model change changes the bitstream, so the chunk schema version pins the model.

Result for RobinTown: 1.99 MB, 4.07 bits/tile, −35% vs zstd-22. This is still above the 1.81-bit two-context estimate; part of that gap is overfit in the estimate and part is real headroom.

4 Palette families: coding characters against each other

The game ships nine families of palette-swap soldiers (Archer00–05, Knight01–03, Guard A/B, …), 48 of 117 characters. Measurement showed they are not palette swaps at pixel level: the variants were re-rendered from re-textured 3D models, so lighting and dithering diverge in ~70% of opaque pixels, and no per-pixel color mapping exists. zstd finds no cross-variant byte repeats, and lossless video codecs fed the variants as frames lose by 15×.

But at the tile level the mapping is nearly functional: where Knight01 has tile #a, Knight02 has one of a small, consistent set of tiles. Conditional entropy: H(Knight02-tile | Knight01-tile) = 0.96 bits, versus ~5.7 standalone. So variants are coded with the base character’s aligned tile as the primary context:

(base-tile, above)  →  base-tile  →  above  →  order-0  →  uniform

Guard A01 drops from 2.34 MB under zstd to 459 KB; the 39 variant characters compress 3.9× compared to coding them independently.

Positional alignment makes this safe: family metadata is byte-identical apart from frame ids, so frame k of a variant pairs with frame k of the base, dimensions verified sprite by sprite. Mismatched sprites are coded standalone.

Which member should be the base? Not the alphabetically first: a full pairwise matrix showed the best “hub” saves 4% over name order, so the converter picks it per family with a sampled conditional-entropy proxy.

5 Shipping it: schema v9

The mission-chunked delivery format (schema v8: content-addressed chunks fetched per mission) gains, per character chunk:

Sprite rows (id, dims, dictionary index) stay as before, but the VQ payloads move into one codec blob per chunk, grids concatenated in bank-id order (other orderings measured no better).

Variant chunks record the base’s name and per-sprite base ids, plus a dependency edge so the base chunk is always fetched and decoded first. A variant chunk whose base is missing fails with an error.

Dictionaries stay in the boot manifest, now frequency-ranked (most-used tile = index 0). The decoder never notices the permutation; it saves 3–5% on data still compressed with zstd.

Conversion output is verified by decoding every shipped sprite back to pixels and comparing with the original bank: byte-identical across all 65,058 demo sprites and 146.6 million pixels, and across all 402,303 fullgame sprites (1.10 billion pixels).

In summary, the data holds three kinds of redundancy: 2-D statistical (tile grids → context modeling), cross-stream functional (families → conditional coding), and long-range exact (RLE animations → LZ). Each bucket gets the coder that matches its redundancy; no single tool wins everywhere.

Why we beat codecs that also model 2-D context

JXL and AV1 also model 2-D context, and they lose 3–17× here. The advantage is inherited from the 2002 VQ pass, which performed the lossy step once at authoring time. That quantization turned a dithered pixel field into a discrete symbol process: 4,096 ids on a lattice. Everything we ship is lossless with respect to those ids (the original renders no longer exist; the quantized bank is what the game displays). An image codec has to reproduce the dither pixel-exactly, and dither is engineered noise. An id predictor works on a small alphabet where a context has either seen the exact symbol or it has not.

Three more factors add to it. Tile ids are categorical, so the numeric prediction image codecs use (gradients, deltas) does not apply. Our statistics persist across a character’s thousands of small frames, with no per-image headers and no shipped model. And cross-variant prediction needs a second character as context, which no standard codec interface accepts.

7 Remaining headroom

The standalone gap to the (optimistic) two-context estimate is about 2×. Sibling-context coding, conditioning a variant on two already-decoded family members, measured −22–25% on third-and-later members and is implemented in the codec; converter wiring is pending. It costs no shipped bytes because the decoder already holds the predecessors via the dependency edges. Decode speed (~1–2M tiles/s single-threaded) is the open engineering item before wasm shipping; chunks are independent, so parallel decode at install is the practical fix. For the animation/patch bucket an xz entropy stage saves 12% vs zstd; custom modeling measured worse there.
