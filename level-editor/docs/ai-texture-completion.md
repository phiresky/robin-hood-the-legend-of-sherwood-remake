# AI completion of occluded textures for the painted-map 3D reconstruction

Research notes, 2026-09-03. Prices/latencies are as listed on vendor pages at time of writing; "unverified" marks things I could not confirm from a primary source.

## 1. 2D inpainting models for strategy A (per-face tiles)

All hosted diffusion inpainters work at roughly 0.5-2 MP internally; a 60x40 tile must be embedded in a larger context crop and/or upscaled first, then downscaled and composited back (see section 3). fal bills per-megapixel models by rounding *up* to the nearest MP, so a 512x512 job costs the same as 1 MP.

Exemplar-guided research models: **Paint-by-Example** (CLIP-embedded reference, loses fine detail), **AnyDoor** (object insertion; Replicate ~$0.0067/run), **RealFill** (per-scene LoRA fine-tune of SD2-inpainting on reference photos, most faithful but needs a training run per building, no official code), **FaithFill/CorrFill/GeoComplete** (2024-25 follow-ups). These target photos and object identity, not painted style; I would not start with them. [PbE](https://ar5iv.labs.arxiv.org/html/2211.13227), [AnyDoor](https://replicate.com/ali-vilab/anydoor), [RealFill](https://realfill.github.io/), [GeoComplete](https://arxiv.org/pdf/2510.03110)

**Tileable output:** the circular-padding hack (patch `Conv2d.padding_mode='circular'`) only works for UNet models (SD1.5/SDXL), not FLUX/Qwen/DiT. Model-agnostic alternatives: inpaint the tile borders in a wrapped layout ([sagieppel](https://github.com/sagieppel/transform-image-into-seamless-tileable-texture-using-stable-diffusion-inpainting)) or **Tiled Diffusion** (CVPR'25, works on latent diffusion generally) [code](https://github.com/madaror/tiled-diffusion). Our faces do not need to self-tile, so seam handling across *adjacent faces* matters more (section 3).

## 2. View-based / 3D methods for strategy B

- **TEXTure** (SIGGRAPH'23): iterative depth-to-image SD inpainting over views with a keep/refine/generate trimap; explicitly supports editing/refining *existing* textures. Closest classic fit for "known partial texture, fill the rest". Self-host, SD1.5-class VRAM, minutes per object. [paper](https://arxiv.org/abs/2302.01721), [code](https://github.com/TEXTurePaper/TEXTurePaper)
- **Text2Tex** (ICCV'23): same idea with progressive generate/update masks; hosted on Replicate (`adirik/text2tex`, text-only, obj input). [replicate](https://replicate.com/adirik/text2tex)
- **Paint3D** (CVPR'24): coarse multi-view stage, then **UV-space inpainting + UVHD refinement** diffusion models trained for lighting-less textures; stage 2 takes `--texture_path`, so it can be run alone on a partial UV atlas. Image prompt via IP-Adapter. Apache-2.0. Wants clean lighting-free textures, which conflicts with our baked-light look. [code](https://github.com/OpenTexture/Paint3D)
- **SyncMVD** (2023), **MVPaint** (CVPR'25), **RomanTex** (2025), **MVDiffusion** (NeurIPS'23): synchronised multi-view denoising for consistency; text/image conditioned, generate a whole texture from scratch, no partial-texture input; SD1.5 + depth/normal ControlNet, meshes ≤ ~40k faces (SyncMVD). MVDiffusion's depth-conditioned mode is the most "scene"-oriented. [SyncMVD](https://github.com/LIU-Yuxin/SyncMVD), [MVPaint](https://github.com/3DTopia/MVPaint), [RomanTex](https://arxiv.org/abs/2503.19011), [MVDiffusion](https://github.com/Tangshitao/MVDiffusion)
- **Hunyuan3D-Paint 2.1**: mesh + one reference image → PBR maps (6-9 views, 512/768 px), ≥21 GB VRAM; the `hunyuan3d-v21` fal endpoint is deprecated, v3/3.1 charge $0.225-0.375 + $0.15 PBR but only as full image-to-3D. Object-centric, regenerates everything, delights rather than baked light. Not a fit. [readme](https://huggingface.co/spaces/tencent/Hunyuan3D-2.1/blob/main/hy3dpaint/README.md), [fal](https://fal.ai/models/fal-ai/hunyuan-3d/v3.1/pro/image-to-3d)
- **TEXGen** (SIGGRAPH Asia'24): feed-forward UV diffusion (700M), paper lists "text-guided texture inpainting" and "sparse-view texture completion" as applications; 24 GB inference; released code lacks an inpainting script. Trained on objects, not façades. [code](https://github.com/CVMI-Lab/TEXGen)
- **TextureDreamer** (CVPR'24): DreamBooth on 3-5 photos + score distillation of a BRDF field; per-object optimisation, not hole filling. **Material Anything** (CVPR'25): estimates PBR from existing textures with confidence masks; irrelevant for us unless we want to de-light. [TD](https://arxiv.org/abs/2401.09416), [MA](https://github.com/3DTopia/MaterialAnything)
- **InTeX** (2024): depth-aware inpainting ControlNet + GUI for region-specific repaint of an existing texture; conceptually exactly "repaint only these faces". [paper](https://arxiv.org/abs/2403.11878)
- **Scene-level, mesh-guided (most relevant to B):** **RoomTex** (ECCV'24) paints a compositional room mesh by a coarse panorama + iterative per-view SDXL-inpaint with depth ControlNet, Apache-2.0, A100/V100 tested. **MeSS** (Aug 2025) textures *city meshes* via cascaded outpainting ControlNets into a Gaussian scene, no public code found. **Text2Room / WonderJourney** (~50 min per scene on a 3090) build geometry while inpainting and are known to drift over long trajectories; we already have geometry, so only their render-inpaint-project loop is relevant. **Geometry-Aware Multiview Scene Inpainting** (2025) and **ObjFiller3D** (reference-guided 3D inpainting, <10 min) handle multi-view holes in images rather than a mesh. [RoomTex](https://github.com/qwang666/RoomTex-), [MeSS](https://arxiv.org/abs/2508.15169), [Text2Room](https://github.com/lukasHoel/text2room), [GeoMVI](https://arxiv.org/abs/2502.13335), [ObjFiller3D](https://arxiv.org/abs/2508.18271)
- **Amodal completion:** **pix2gestalt** (SD fine-tune, 22-28 GB demo) completes whole objects in 2D; **Amodal3R** (TRELLIS-based) regenerates a complete 3D object from an occluded view; **Gen3DSR** inpaints occluded object crops with a fine-tuned SD before per-object 3D. All replace geometry we already know, so useful only as inspiration for "complete the building crop, then re-project". [pix2gestalt](https://github.com/cvlab-columbia/pix2gestalt), [Amodal3R](https://huggingface.co/Sm0kyWu/Amodal3R), [Gen3DSR](https://andreeadogaru.github.io/Gen3DSR/)
- **Gaussian-splat inpainting** (Gaussian Grouping, InFusion, GSFix3D 2025): needs a trained 3DGS scene and per-scene optimisation; no hosted service. Only worth it if we move to splats. [GSFix3D](https://arxiv.org/html/2508.14717)

Nothing in this group is hosted on fal/replicate except Text2Tex and full image-to-3D pipelines; everything else is self-host at 16-24 GB VRAM, minutes per object, and none respects a fixed oblique-orthographic painted style out of the box (they use perspective views and photoreal SD priors).

## 3. Practical tricks for this dataset

- **Context crop, not bare tile.** Send the tile embedded in the *map-space* crop of the whole building (say 768-1024 px square, padded), with the hole as mask; the model then sees neighbouring walls, roof, shadows and light direction. Re-project the result into the face tile afterwards. This is essentially one TEXTure/RoomTex "view" and works with any 2D inpainter.
- **Protect known pixels yourself.** Every hosted model except FLUX Fill pro re-encodes through a VAE or regenerates the whole image; always alpha-composite the original pixels back and keep a 2-4 px feathered band inside the hole for blending.
- **Upscale tiny tiles.** 2-4x nearest/lanczos upscale of the context crop before inpainting, downscale after (ComfyUI guidance for FLUX Fill: upscale first when the masked area is small). Batch several small faces of one building into one 1 MP crop to avoid paying 1 MP minimum per 60x40 tile.
- **Style reference.** Options in order of directness: Ideogram V3 edit style refs; FLUX general inpainting IP-Adapter; multi-image editors (Nano Banana 2, FLUX.2 pro, Seedream) given the building crop + a 1024 px map crop with "same painter, same light from upper-left"; or train one FLUX LoRA on ~100 crops of the map (fal supports Fill/Kontext LoRAs) for a fixed style.
- **Light direction.** Put it in the prompt and, for view-based passes, pick views where the visible lit faces dominate; for back walls tell the model "shadow side". Expect drift regardless; a post-pass that matches per-face mean luminance to the nearest visible face of the same orientation is cheap insurance.
- **Cross-face seams.** Inpaint whole buildings in map space (all faces of one building in one crop) rather than face by face, or run strategy B views so adjacent faces are denoised together. Dilate masks a few px across face boundaries.
- **Multi-view consistency for B.** Order views so each new view has ≥50 % already-textured pixels (TEXTure trimap), project back only pixels facing the camera within ~60°, and stop after 3-6 passes; the error-accumulation problem in Text2Room is what limits this.
- **Cost, 3000 tiles vs 50 views:** at fal's 1 MP minimum, 3000 tile jobs ≈ $105 (FLUX Fill dev), $90 (Qwen inpaint), $117 (Gemini 2.5), $120 (Kontext pro), $180 (Ideogram balanced), $225 (FLUX general + IP-Adapter). Batching ~5 faces per crop cuts this to ~$20-45. 50 view passes at 1-2 MP ≈ $2-8 for any model, plus far more engineering.

## 4. Recommendation

1. **Start with strategy A in map space using FLUX.1 Fill [dev] on fal** (`flux-lora/inpainting`, $0.035/MP): one 1 MP crop per building with all its holes masked, prompt like "painted medieval town map, oblique view, timber-framed wall in shadow, same style". Cheap (~$20-40 per map with batching), 2-5 s per call, mask is respected, and it is the model most people report as best at continuing existing texture. Composite with alpha, feather, luminance-match. Compare against Qwen inpaint and Nano Banana 2 (multi-reference) on 20 buildings before scaling.
2. **If style drifts, add a reference channel** rather than switching families: FLUX general inpainting with IP-Adapter scale ~0.5, or a small map-style LoRA (train once on fal, reuse for every map). Ideogram V3 edit is the cheapest hosted "mask + style ref" fallback.
3. **Treat strategy B as a second phase**, self-hosted, using the TEXTure/RoomTex loop with the same FLUX Fill model: 4-6 oblique views per district, project back, only where A leaves visible seams on long back walls. Expected cost is negligible; expected effort is days, and the perspective-trained priors will fight the orthographic look.

Main risks: style drift on large holes (mitigate with context crops + reference/LoRA), seams between separately inpainted faces (mitigate by per-building crops and feathering), wrong light direction on back walls (prompt + luminance post-match; no model conditions on light direction explicitly), and hidden per-call costs from fal's 1 MP round-up (batch faces).
